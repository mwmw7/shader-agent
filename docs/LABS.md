# 30명 실습 운영: 3명 × 10팀

역할은 업무 설명자, 노드 설계자, 검증 담당자로 나누고 실습마다 교대합니다. 아래 시간은 권장 운영값입니다.

## 실습 1 · 업무를 에이전트와 툴로 분해 (15분)

디자이너 이미지 전달 → Shadertoy 유사 효과 탐색 → LLM 수정 → Android 포팅 → 디자이너 피드백이라는 기존 흐름에서 판단과 실행을 분리합니다. 이 실습 코드에서는 외부 검색 대신 원본 로컬 예제를 사용합니다.

한 노드마다 입력, 판단 책임, 출력 스키마, 허용 툴, 선행조건, 실패/완료 조건을 기록하세요. “영상을 만들기”와 “어떤 영상 검사를 수행할지 판단하기”를 구분하세요. 결과물은 노드 명세서 1장입니다.

## 실습 2 · 호출 방식 비교 (20분)

같은 모델·요청·참조 이미지로 고정 모드와 선택 모드를 각각 실행합니다. `events.jsonl`에서 에이전트 순서, 모델 호출 수, 예제 검색 여부를 비교하세요. 시간 차이를 모델 품질 차이라고 바로 해석하지 않습니다.

`harness-policy.ts`의 `permittedNext()`를 읽고, 평가 전 AGSL 실행이 왜 불가능한지 설명하세요. 테스트의 오케스트레이터가 미등록 노드를 제안하는 실패 주입 사례를 확인합니다. 허용 목록을 넓히는 변경은 입출력·선행조건 검사와 함께 제출하세요.

## 실습 3 · 평가 피드백 루프 (20분)

“빗줄기의 깊이와 속도 차이” 같은 구체적인 요구를 추가합니다. 평가 JSON의 프레임 이름과 실제 PNG를 비교하세요. 통과하지 못하면 새로운 revision의 영상·프레임·평가가 만들어졌는지 확인합니다.

`npm run test:pipeline`은 평가를 한 번 실패시키는 테스트 대역으로 실제 재렌더 루프를 재현합니다. 이 대역은 실습 결과의 시각 품질을 평가한 모델이 아니라, 분기 검증용입니다. 실제 모델 실행과 구분해서 기록하세요.

오래된 `evidenceRevision`이나 존재하지 않는 프레임 이름으로 통과시키려 하면 어떤 검사에서 차단되는지 설명하세요.

## 실습 4 · 툴 권한과 취소 (15분)

`tests/tools.test.ts`에서 render 역할의 `agsl.convert` 호출 차단을 확인합니다. UI에서 실행 중 취소를 눌러 추가 모델/툴 호출이 멈추는지 확인하고, `run.cancelled` 이벤트와 종료 이유를 제출하세요. 단순히 버튼만 비활성화하는 구현과 비교해 설명합니다.

## 실습 5 · 자신의 업무에 적용 (20분)

공개 가능한 반복 업무를 선정하고, 기존 역할 1개를 다른 역할로 바꾸는 설계를 작성합니다. 공유 등록 목록, 프롬프트, JSON 스키마, ACL, 그래프 간선, 테스트 중 어디를 함께 바꿔야 하는지 표시하세요.

서로의 설계에 금지된 호출·오래된 증거·누락된 파일을 입력하는 검증 사례를 1개씩 만듭니다. 평가 기준은 노드 개수가 아니라 실행 경계와 증거의 명확성입니다.

제출물: 노드 명세, 실제 실행 로그, 허용/차단 근거, 평가 프레임, 종료 조건 기록. Android 결과를 테스트하지 않았다면 그 상태를 그대로 표시합니다.
