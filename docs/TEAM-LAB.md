# 3명 × 10팀: 에이전트 구성 비교 실습

동일한 요청과 참고 이미지로 팀별 역할·프롬프트·실행 순서가 결과에 미치는 영향을 비교합니다. 노드가 많거나 자기 점수가 높다고 더 좋은 결과라고 결론내리지 않습니다.

## 실행 준비

Node.js 24, FFmpeg, 설치된 로컬 비전 모델과 추론 서버가 필요합니다. FFmpeg와 모델은 이 프로젝트에 포함하지 않습니다. Chromium은 아래 명령으로 설치합니다.

```bash
cd team-lab
node --version
npm ci
npm run setup:renderer
npm run doctor
npm start
```

브라우저로 열려면 `npm run serve`를 사용합니다. Ollama는 기존 프로세스를 종료한 뒤 별도 터미널에서 실행합니다.

```bash
OLLAMA_NO_CLOUD=1 ollama serve
```

앱 설정에서 로컬 서버를 등록하고 설치된 **이미지 입력 지원 모델**을 조회·검증합니다. 모든 팀은 동일한 모델 버전·양자화·서버 설정을 사용합니다. 텍스트 전용 모델이나 외부 API를 대체 경로로 사용하지 않습니다.

## 역할과 시작 구성

각 팀의 3명은 요청·기준 담당, 에이전트 구성 담당, 실행·증거 담당을 맡고 다음 시도에서 교대합니다. 처음에는 `01팀`부터 `10팀`까지 독립적인 설정이 준비됩니다. 배포용 `samples/teams/team-01.json`부터 `team-10.json`도 포함했습니다. 팀 JSON 불러오기에서 열고 이름·가설·프롬프트를 바꿔 저장하세요.

| 시작 구성 | 기본 팀 | 검증할 설계 가설 |
|---|---|---|
| 핵심: 분석 → 제작 → 렌더링 → 평가 | 01·04·07·10팀 | 핵심 역할만으로 공통 요청을 충족하는가? |
| 핵심 + 구도·색상·움직임 계획 | 02·05·08팀 | 제작 전 전문 계획이 요구 충족도를 개선하는가? |
| 핵심 + 실제 프레임 검토 | 03·06·09팀 | 별도 검토 의견이 수정 정확도를 개선하는가? |

모든 시작 구성에는 선택 역할인 AGSL 이식이 활성화되어 있습니다. 비교 시 모든 팀에서 같은 상태로 유지합니다. 기본 실행 방식은 고정 순서이며, 오케스트레이터 방식은 별도 실험으로 비교합니다.

모든 노드는 실제 LLM 호출로 판단합니다. 계획과 검토를 추가해도 툴 권한은 역할별 서버 정책으로 고정됩니다. 분석·제작·렌더링·평가는 필수이며, 계획은 최대 3개, 검토는 최대 2개입니다. 노드 ID는 영문 소문자로 시작하고 소문자·숫자·하이픈만 사용합니다. 팀 이름·아이콘·노드 목적·프롬프트는 편집할 수 있습니다.

**목적**은 그 노드가 해야 할 일이고, **설계 가설**은 그 구성이 개선할 것으로 예상하는 점입니다. 가설을 지지하려고 점수를 높이거나 다른 팀과 결과를 억지로 다르게 만들지 않습니다. 비슷한 좋은 결과가 나오면 그 사실을 기록합니다.

## 통제된 실험

1. 요청·이미지를 한 번 정하고 팀 전체에 동일하게 적용합니다. 요청에는 구도, 색, 움직임, 피해야 할 현상처럼 사람이 판정할 수 있는 기준을 적습니다.
2. 모델, 최대 수정 횟수, 모델 호출 예산, 렌더링 설정을 공통으로 유지합니다. 처음에는 역할 구성만 바꾸고 나머지를 고정합니다. 장비가 다르면 실행 시간 비교에 장비 차이를 함께 기록합니다.
3. 팀 설정을 저장한 뒤 실험을 실행합니다. 각 실행에는 당시 구성 스냅샷이 남으므로 이후 설정 변경과 구분할 수 있습니다.
4. 실제 경로, 모델 호출 수, 수정 횟수, 소요 시간, 종료 사유와 0 / 1.25 / 2.75초 프레임을 비교합니다. 실패·중단·취소를 완료로 표시하지 않습니다.
5. 같은 조건으로 **최소 3회 반복**합니다. 한 번의 좋은 결과만 골라 제출하지 말고 실패한 시도도 포함합니다.
6. 팀 이름·구성·자가평가 점수를 가린 영상과 같은 시점의 프레임을 제시하고 사람이 블라인드 비교 투표를 합니다. 투표 기준은 요청 충족, 참고 이미지의 구도·색 재현, 움직임의 자연스러움입니다. 움직임은 정지 프레임만으로 판정하지 말고 MP4 전체를 확인합니다.

자가평가 점수는 각 실행의 수정 피드백입니다. 구성과 프롬프트가 다르면 점수 기준도 달라질 수 있으므로 팀 간 공통 품질 순위로 사용하지 않습니다. 품질과 모델 호출 수·소요 시간을 함께 기록하되 하나의 숫자로 합치지 않습니다.

## 다른 PC의 결과 모으기와 발표

실험의 비교 패키지 JSON에는 공통 입력·입력 해시, 당시 팀 구성, 실행 기록, 소스와 실제 PNG 프레임이 포함됩니다. MP4와 프로바이더 API 키·비밀 설정은 포함하지 않습니다. 이미지·요청·프롬프트가 담기므로 공유 가능한 자료만 사용합니다. 내보낸 JSON 여러 개를 진행자 PC에서 가져오면 에이전트나 셰이더를 재실행하지 않고 하나의 비교 자료로 모을 수 있습니다. 가져온 결과는 프레임·코드를 비교하며, 움직임 비교용 MP4는 원래 실행한 PC에서 별도로 준비합니다.

**입력 해시가 같은 실험끼리만 비교**합니다. 해시가 다르면 요청·참고 이미지·모델·예산 등의 차이를 확인하고 공통 입력으로 다시 실행합니다. 같은 해시라도 PC별 실제 모델 파일, 양자화, 추론 설정과 장비가 동일한지는 별도로 확인합니다. 입력 해시는 실험 조건 비교를 돕는 값이며 파일의 진위나 품질을 인증하지 않습니다.

실험의 HTML 보고서를 내려받으면 인터넷 없이 한 파일로 발표할 수 있습니다. 공통 입력과 참고 이미지, 팀별 동일 시점 PNG, 실행 경로, 구성·프롬프트, 수정 이력과 소스를 포함합니다. 접힌 항목을 열어 자세히 볼 수 있습니다. 보고서는 자동 순위를 만들지 않으며 없는 프레임을 샘플 이미지로 채우지 않습니다. 가져온 결과를 모은 보고서와 블라인드 투표 결과를 함께 발표합니다.

제출물은 설계 가설, 사용한 팀 설정, 최소 3회 실행 기록, 비교 패키지, 발표용 HTML, 블라인드 투표 결과입니다. AGSL 생성은 Android 실기기 검증을 뜻하지 않습니다.

## 검증 범위

자동 테스트의 모델 대역은 정책과 분기를 검증하기 위한 것입니다. 앱은 운영 실행에 미리 만든 모델 응답이나 성공 영상을 넣지 않습니다. 실제 로컬 모델 추론·시각 품질·Android 실행을 확인하지 않았다면 확인하지 않았다고 기록합니다. 환경과 기존 검증 범위는 `docs/VALIDATION.md`를 참고하세요.
